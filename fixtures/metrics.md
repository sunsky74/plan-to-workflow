# 真实切片度量

A 期改动全部来自**事后复盘**（会话日志 + 人工 steer）。这张表用来回答唯一重要的问题：
**它们真的让切片变快、变少干预了吗？** 填不满两行就不做 B 期。

## 字段口径

| 字段 | 怎么量 |
|---|---|
| 派发前耗时 | Step 2 开始 → `subagent(...)` 发出 |
| 执行墙钟 | 派发 → workflow 返回或停机 |
| 无效等待占比 | 子 agent 处于 `status` 探活后确认「在转圈」的时长 / 执行墙钟 |
| 人工介入 | 用户消息数 + 编排方主动 `steer` 次数（都算干预） |
| 生成失败 | `validate`/`dryrun`/`coverage` 判失败后改 workflow.js 的轮数 |
| 续跑次数 | `report.resumes` 长度 |
| UNKNOWN | `report.resumes` 里 `reason=gate-unknown` 的次数 |

## 记录

| 切片 | 模式 | 派发前耗时 | 执行墙钟 | 无效等待占比 | 人工介入 | 生成失败 | 续跑次数 | UNKNOWN |
|---|---|---|---|---|---|---|---|---|
| alert P1（基线，A 期之前） | 标准 | 14m | 73m | 41% | 3 | 6 | — | — |
| | | | | | | | | |

基线那一行是 A 期所有改动的出发点：73 分钟里有 30 分钟是无效等待，两次卡死各 49 / 51 分钟。

## 决定 B 期的门槛（满足任意两条才做）

- 每片生成失败 ≥ 2
- 改 workflow.js 文本占派发前耗时 ≥ 30%
- 后续 ≥ 5 片或 ≥ 2 个项目
- 门禁耗时占执行墙钟 ≥ 35%

不满足就**停在 A 期**。B 期（spec + 单源 runner + 生成器）是把「生成 workflow.js 靠手改字符串」换成结构化生成——只有这项成本真的占大头时才值得做。
